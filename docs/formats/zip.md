# ZIP spec (input and output)

ZIP is not a photo format, so there is no metadata to strip. It matters because people hand us a folder as one `.zip`, and want one `.zip` back. This is the same discipline as the image formats: write down exactly what we read and write before writing code.

## Layout

A ZIP file is a list of entries, then a **central directory** at the end that indexes them. Readers start from the end.

```
[local header + data] [local header + data] ...      one per file
[central directory header] [central directory header] ...   one per file, repeats the metadata
[end of central directory record, "EOCD"]             last 22 bytes (plus an optional comment)
```

All integers are **little-endian**.

```
local header          50 4B 03 04  version(2) flags(2) method(2) time(2) date(2) crc32(4) compSize(4) size(4) nameLen(2) extraLen(2) name extra
central header        50 4B 01 02  madeBy(2) needed(2) flags(2) method(2) time(2) date(2) crc32(4) compSize(4) size(4) nameLen(2) extraLen(2) commentLen(2) disk(2) internalAttrs(2) externalAttrs(4) localOffset(4) name extra comment
EOCD                  50 4B 05 06  disk(2) cdDisk(2) entriesOnDisk(2) entriesTotal(2) cdSize(4) cdOffset(4) commentLen(2)
```

Why the central directory is the source of truth: when flag bit 3 is set, the local header's sizes and CRC are zero and a "data descriptor" follows the data. The central directory always has the real values, so we read sizes from there.

## Reading (input)

| Case | Action |
|---|---|
| method 0 (stored) | copy the bytes |
| method 8 (deflate) | inflate with the browser's `DecompressionStream("deflate-raw")` |
| any other method | reject: unsupported |
| encrypted (flag bit 0) | reject: unsupported |
| ZIP64 (sizes or counts of `FFFF`/`FFFFFFFF`) | reject: unsupported. Our limits keep every batch far below 4 GB |
| directory entry (name ends with `/`) | skip |
| `__MACOSX/`, `._name`, `.DS_Store` | skip: macOS junk, never a photo |
| a stored CRC-32 that does not match the data | reject: corrupt |
| no EOCD, or offsets that point outside the file | reject: corrupt |

**Zip bombs.** A 50 KB ZIP can inflate to gigabytes. Declared sizes are checked before inflating, and the inflate loop itself stops the moment the output passes the declared size or the limits, so memory is never allocated for an oversize entry.

**Names.** Only the last path segment is used (split on `/` and `\`), so a name like `../../x.jpg` can never mean anything outside the batch. Duplicate names get ` (2)`, ` (3)`.

## Writing (output)

- **Method 0 (stored).** JPEG, PNG and WebP are already compressed, so deflating them gains almost nothing and costs time.
- **Fixed timestamp** of 1980-01-01 00:00 (the earliest a ZIP can store), so the archive does not record when the user cleaned their photos.
- **UTF-8 names** with flag bit 11 set.
- Version made by is "MS-DOS, 2.0", with zero external attributes: no Unix owner or permission bits are recorded.
- No extra fields, no comments.
- Throws if there are more than 65,535 entries or the archive would pass 4 GB.

## Limits (a product decision, in `src/lib/limits.ts`)

| Limit | Value |
|---|---|
| photos per batch | 200 |
| size of one photo | 100 MB |
| total size of a batch | 500 MB |
