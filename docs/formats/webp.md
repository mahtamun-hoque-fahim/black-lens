# WebP chunk map

Written before the WebP stripper (Council PRE-BUILD condition 1). The code in `src/lib/metadata/webp/` must match this table.

## How a WebP file is laid out

WebP is a RIFF container. The same idea as PNG chunks, with three differences that matter:

```
"RIFF"  <file size - 8: 4 bytes, LITTLE-endian>  "WEBP"
then chunks:  <FourCC: 4 ASCII bytes>  <size: 4 bytes, LITTLE-endian>  <payload>  <1 zero pad byte if size is odd>
```

1. **Little-endian**, where PNG and JPEG are big-endian.
2. **No checksums.** Nothing detects damage inside a chunk, so structure checks are all we have.
3. **The size field at the top is part of the file.** Removing chunks changes the total, so the `RIFF` size must be rewritten. A wrong size makes decoders refuse the file. This is the part that is easy to get wrong.

The `RIFF` size also defines where the image ends. Bytes after `8 + size` are not part of the file, which is where trailing data hides. Every chunk is padded to an even length.

### Simple and extended files

A simple file is `RIFF`, then one `VP8 ` (lossy) or `VP8L` (lossless) chunk. It cannot hold metadata at all.

Anything with metadata, alpha beside lossy data, a colour profile or animation starts with a `VP8X` chunk, a 10-byte header:

```
byte 0     flags:  0x20 ICC profile   0x10 alpha   0x08 EXIF   0x04 XMP   0x02 animation   (0xC1 reserved)
bytes 1-3  reserved, must be zero
bytes 4-6  canvas width - 1   (24 bits, little-endian)
bytes 7-9  canvas height - 1
```

The flags must agree with the chunks that follow. So when we remove `EXIF` and `XMP `, we must also clear their flag bits, or the file lies about its own contents. The reserved bits and bytes are cleared too, since they could carry hidden data.

Chunk order in an extended file: `VP8X`, `ICCP`, `ANIM`, image data (`ALPH` + `VP8 `, or `VP8L`, or `ANMF` frames), then `EXIF`, then `XMP `.

## Rule: default deny

Same as the other formats. Only the chunks in the table below are copied. An unknown chunk is removed.

## Chunk table

| Chunk | Name | Action | Why |
|---|---|---|---|
| `VP8 ` | Lossy image data | keep, byte for byte | The pixels |
| `VP8L` | Lossless image data | keep, byte for byte | The pixels |
| `ALPH` | Alpha channel | keep, byte for byte | Transparency for lossy images |
| `ANIM` | Animation parameters | keep | Background colour and loop count |
| `ANMF` | Animation frame | keep; unknown sub-chunks removed | A frame holds a 16-byte header then its own sub-chunks (`ALPH`, `VP8 `/`VP8L`). Anything else inside is removed and the frame size rewritten |
| `VP8X` | Extended header | keep, **flags rewritten** | Clear EXIF, XMP, and reserved bits; set or clear the ICC and EXIF bits to match what is really there. Canvas size is kept |
| `ICCP` | ICC colour profile | keep (switch can remove) | Colours shift without it. When removed, the ICC flag is cleared |
| `EXIF` | EXIF | **replace** | Remove everything. If the original held a valid Orientation (1 to 8), write a new `EXIF` chunk with only that tag and set the EXIF flag |
| `XMP ` | XMP | remove | Author, edit history, tool names. Note the trailing space in the name |
| any other chunk | Unknown | remove | Not needed to display |
| anything after the `RIFF` size | Trailing data | remove | Appended payloads, a second file |

## Orientation, in bytes

WebP stores EXIF bare, like PNG: the payload is the TIFF structure itself (some writers wrongly keep an `Exif\0\0` prefix; the reader tolerates it). The chunk we write is 4 + 4 + 26 = 34 bytes, already even so no pad byte:

```
45 58 49 46                      "EXIF"
1A 00 00 00                      payload size 26, LITTLE-endian (the TIFF inside is still big-endian "MM")
4D 4D 00 2A  00 00 00 08         byte order, magic 42, IFD0 at offset 8
00 01                            one entry
01 12  00 03  00 00 00 01  00 06 00 00     Orientation, SHORT, count 1, value 6
00 00 00 00                      no next IFD
```

It goes last, after the image data, which is where the WebP layout puts it. When there is no Orientation to keep, there is no `EXIF` chunk and the flag is clear. A simple file with no `VP8X` is left untouched.

## What "identifying" means for the verifier

After stripping, the re-read check allows only:

- the chunks in the keep rows
- `ICCP` unless removal was requested
- at most one `EXIF`, holding exactly one tag: Orientation
- `VP8X` flags that match the chunks present, with no reserved bits set
- inside `ANMF`, only `ALPH`, `VP8 ` and `VP8L`
- zero bytes after the `RIFF` size, and a `RIFF` size that equals the file length minus 8

## Image data check

"Image data unchanged" means these are byte-identical before and after: every `VP8 `, `VP8L`, `ALPH` and `ANIM` chunk, each `ANMF` frame header with its allowed sub-chunks, and the canvas size inside `VP8X`.
